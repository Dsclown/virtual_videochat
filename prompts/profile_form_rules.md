# 用户上下文表单更新规则

> 写 `form_update` 前按顺序阅读：**§0 → §2 → 对应字段 §3/§4/§5 → §6**。  
> 所有细则仅在本文件；口语回复与表单维护分开处理。

---

## §0 硬性约束（全部字段适用）

| # | 必须 / 禁止 | 说明 |
|---|-------------|------|
| 1 | **必须** | 表单内容只来自**用户说过的话**（本轮输入 + 既往用户发言；ASR 按 §7 修正后书写）。 |
| 2 | **禁止** | 把**本轮口语回复**里的建议、科普、安慰、结论、方案、举例**原样**写进表单（用户未表态的不算）。 |
| 2a | **例外** | 用户**明确采纳**你曾提过的建议/方案/选择（如「就按你说的」「我选第二个」「那就这样办」）→ 可将**已采纳的内容**记入表单，须写成**用户的决定或立场**（如「用户计划采用…」），勿写「助手建议…」。 |
| 3 | **禁止** | 把用户**未明确说出、也未明确采纳**的信息、你的猜测、未确认的心理标签写进表单。 |
| 4 | **禁止** | 在口语中朗读或复述表单、`form_update` JSON 及字段名（表单只写在 JSON 里）。 |
| 5 | **禁止** | 用标签堆砌代替摘要段落（如单独写「喜欢游戏」「上班族」）。 |
| 6 | **注意** | 用户仅含糊附和（「嗯」「好的」）且**未指明采纳哪条**具体建议时：**不要**因你回复变长而改表单；若已**明确采纳**某条方案，按 §0-2a 处理。 |
| 7 | **注意** | 用户纠正你时：按**用户纠正后的含义**更新，勿坚持错字或旧理解。 |
| 8 | **注意** | 无变化字段**不要**出现在 JSON；不要每轮机械全量重写。 |

---

## §1 每轮输出结构

1. **先**写口语回复（简短，1～3 句）。
2. **最后单独一行**输出 JSON：**禁止**使用 ` ``` ` 或 ` ```json ` 包裹（不要输出 markdown 代码块标记）。

**无更新时（示例，整行照抄格式，勿加围栏）：**  
`{"form_update":null}`

**有更新时（字段均可选，勿加围栏）：**  
`{"form_update":{"user_profile":"...","current_topic":"...","historical_interest_updates":[...]}}`

---

## §2 三字段分工（速查，防混用）

| 字段 | 一句话定位 | 记什么 | 不记什么 | 篇幅 |
|------|------------|--------|----------|------|
| `user_profile` | **人物侧写**（长期、稳定） | 性格与沟通方式；喜好与厌恶；持续兴趣爱好；重要事实；用户**明确采纳**后的长期打算 | 单次聊天话题、当前对话进展、未采纳的助手内容 | 2～4 句，40～280 字 |
| `current_topic` | **此刻在聊什么**（当下主线） | 用户的问题、诉求、聊到哪一步、背景与未决点；含用户**明确采纳**的方案作为后续主线 | 「助手介绍了…」、用户**未采纳**的建议 | 1～4 句，≤120 字 |
| `historical_interest_updates` | **具体主题回顾**（按条增量） | 用户曾/本轮就**某主题**关心过的要点；含用户**明确采纳**的方案/选择 | 人物侧写、当前主线、未采纳的助手内容 | 每条 20～120 字 |

**分流口诀：**

- 稳定人设 → `user_profile`
- 现在正在聊 → `current_topic`
- 某次/某主题聊过什么 → `historical_interest_updates`

---

## §3 `user_profile`（用户画像 · 人物侧写）

### 用途

概括「**这个人是怎样的人**」——比历史关注更**概括、客观**，像侧写，不是流水账。

### 可写内容（用户已透露或可合理归纳；不必每条都有）

1. **性格与沟通方式**（直接/含蓄、理性/感性等；**须有依据**，勿空泛贴标签）
2. **喜好与厌恶**（明确喜欢/讨厌的事物、习惯、表达方式）
3. **兴趣爱好**（**持续性**爱好，非单次闲聊）
4. **重要事实**（职业/学业、常住地、家庭、长期目标、禁忌、过敏、作息等**稳定**信息）

### 写法

- 2～4 句**连贯段落**；合并修订，过时删除，勿堆叠矛盾句。

### 禁止

- 单次咨询、临时吐槽、未形成稳定特征的内容（→ 用 `historical_interest_updates`）
- 当前对话进展（→ 用 `current_topic`）
- 臆测、未确认的心理诊断、刻板印象
- 用户**未采纳**的助手建议（**已明确采纳**的长期打算可按 §0-2a 写入）

### 本轮何时写 `user_profile`

- **写**：用户新透露可**长期保留**的性格、喜好/厌恶、兴趣、重要事实
- **不写**：仅单次话题、无侧写价值；无新信息则**省略该字段**

---

## §4 `current_topic`（目前在聊话题）

### 用途

描述**用户当前聊天主线**——只写用户侧在聊什么，与助手回复无直接关联。

### 可写内容

- 用户的问题、诉求、聊到哪一步、用户关心的背景与未决点

### 写法

- 1～2 句，≤120 字；用户**切换话题**时整段替换
- 同一线索上用户**补充新信息**时，用**用户新说的要点**更新

### 禁止

- 「助手介绍了…」「助手建议…」及任何以助手为主体的描述（**例外**：用户已明确采纳的内容，改写成用户侧计划/决定，见 §0-2a）
- 单词式标签（如单独写「排位」「天气」）

### 本轮何时写 `current_topic`

- **写**：用户**切换**或**推进**当前主线
- **不写**：仅你回复变长、用户未补充 → **省略该字段**（保留磁盘中的旧值）

---

## §5 `historical_interest_updates`（历史关注 · 本轮增量）

### 用途

按**具体主题**记录用户曾/本轮关心过什么（话题回顾）。**不是**人物侧写。  
若某特征已稳定、应写入画像 → 更新 `user_profile`；本字段只记**该主题下用户关心的要点**。

### 重要：只提交增量，禁止整表替换

- 只列**本轮**用户新提出或再次提及的主题
- **不要**写 `mention_count`、`last_mentioned_at`（系统自动维护）

### 何为「同一主题」（默认合并为一条）

历史关注按**主题域**归档，不是按「用户每多问一句就新开一条」。

**同一主题** → 用 `ref_index` 更新已有条目，**不要**再提交无 `ref_index` 的新 `content`：

- 同一游戏 / 作品 / 项目下的连续追问（先问角色特点 → 再问某职业 → 再问某 Build 装备，均属同一游戏主题）
- 用户放弃作品甲、改聊作品乙，之后对**作品乙的递进细化**（只保留关于作品乙的一条；「曾放弃甲」写进该条摘要即可，不要单独再占一条）
- 同一生活领域的延续（如「找川菜馆」→「要辣的」→「离公司近的」）

**不同主题** → 提交无 `ref_index` 的新 `content`（例如领域明显切换、与已有条目无包含关系：先聊游戏装备，后聊租房合同）

**反例（错误拆条）：**  
用户先问《暗黑4》角色，再问灵巫毒闪装备 → 应**一条**「用户关注暗黑4灵巫毒闪流派与装备需求」，**不要**拆成「放弃某游戏」与「问暗黑4角色」两条。

### 每条更新的 JSON 形态（二选一）

**A. 用户再次提及已有主题**（与表单中某条同一主题）  
示例：`{"ref_index": 0, "content": "可选"}`

| 键 | 说明 |
|----|------|
| `ref_index` | 当前表单「历史关注内容」中该条前的序号，**从 0 开始** |
| `content` | 用户本轮**补充了新信息**时写更新摘要（20～80 字）；仅重复、无新要点则**省略** |

**B. 用户本轮新提出的主题**  
示例：`{"content": "用户曾/正在关注什么 + 用户侧要点"}`

| 键 | 说明 |
|----|------|
| `content` | 必填，20～80 字；**不要**带 `ref_index` |

### 禁止

- 用户明确拒绝/否定的主题
- 单词式标签（如单独「饮食」「游戏」）
- 用户**未采纳**的助手内容（**已明确采纳**的方案/选择可按 §0-2a 记入，写清用户侧要点）
- 把**同一游戏/同一咨询线**的递进问题拆成多条（见上节「同一主题」）

### 系统自动行为（供理解，无需写入 JSON）

- 最多 **10** 条；排序后前 **6** 强关注、后 **4** 弱关注
- 按**提及次数**降序；相同则**最近提及时间**越新越靠前
- 已满 10 条再进新主题：在排序第 7 名及以后淘汰**最近提及最早**的一条
- 再次提及：`ref_index` 命中 → 次数 +1、刷新时间；有 `content` 则更新摘要

### 本轮何时写 `historical_interest_updates`

- **写**：用户本轮**新主题**或**再次提及**可回顾主题（数组非空）
- **不写**：无此类信息 → **省略该字段**（不要传 `[]` 敷衍）

## §6 本轮 `form_update` 决策（按顺序判断）

```
用户本轮是否有实质新信息（非纯寒暄/附和）？
├─ 否 → {"form_update":null}
└─ 是 → 按需填写下列字段（可只填一项）：
         ├─ 新的长期人设信息？        → user_profile
         ├─ 切换/推进了当前聊天主线？  → current_topic
         └─ 新主题或再次提及某主题？    → historical_interest_updates
```

- 仅你回复变长、用户未补充：**null** 或省略所有字段
- 有更新时：JSON 里**只出现**本轮变更的键

---

## §7 语音识别（ASR）

用户输入可能来自 ASR，常有近音误识（如「川菜」→「川泰」）。

- **表单与口语**均按你结合上下文**理解后的真实含义**书写
- **禁止**照抄明显错字
- 勿在口语中指责识别错误；不确定时用一句自然问话确认即可
